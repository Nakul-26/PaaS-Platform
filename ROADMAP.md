| 2 | Multi-Node Infrastructure | ✅ | Started 2026-08-18, exit criteria automated and passing 2026-08-21: [`docs/phases/phase-2-multi-node.md`](docs/phases/phase-2-multi-node.md). Task 1 done: NATS added to `infrastructure/docker-compose.yml`; `EventBus` interface + NATS adapter (core + JetStream) in `internal/eventbus`; subjects/schemas documented in `docs/nats-contract.md`; round-trip integration test against a real NATS/JetStream container passing. Task 2 done: `0007_nodes_containers.sql` migration (`nodes`/`containers`, no RLS — infrastructure, not tenant-scoped); `NodeRepository`/`ContainerRepository` in `internal/db`; integration test against real Postgres covering register/re-register/heartbeat/status-transition flows passing. Task 3 done: `services/worker/internal/nodeagent` publishes `node.<id>.register` once at startup (node ID generated and persisted locally so restarts re-register the same node) then `node.<id>.heartbeat` on a configurable interval (default 5s); purely additive alongside the untouched HTTP contract, connects to NATS with a 30s retry-then-degrade-to-HTTP-only loop since the nats image has no exec healthcheck to depend on; integration test builds and runs the real worker binary against a real NATS container, confirming registration + scheduled heartbeats arrive. Task 4 done: the node agent now also subscribes durably (JetStream, `NODE_ASSIGNMENTS` stream) to its own `node.<id>.assign` subject; on message it drives the same `ContainerRuntime` pull/create/start path the HTTP `POST /v1/containers` handler uses, then publishes the outcome durably (`NODE_STATUS` stream) on `node.<id>.status`, mapping `internal/runtime.Status` onto `containers.status`'s vocabulary (`exited`+exit-code splits into `stopped` vs `crashed`); integration test publishes an assignment directly (no scheduler yet), confirms a real container starts on the real Docker daemon and a matching status message comes back. Task 5 done: new `services/scheduler` binary (`internal/scheduler` package) — a node registry consuming `node.*.register`/`node.*.heartbeat` (core NATS wildcard subscribe) to upsert `nodes` rows, plus a periodic liveness sweep marking a node `unreachable` once its `last_heartbeat_at` exceeds a configurable timeout (default 15s, swept every 5s); placement consuming `placement.requested` (JetStream `PLACEMENT` stream), applying filter-then-score (§2.2: filter unhealthy/zero-capacity nodes, score the rest by lowest current non-terminal-container count), writing a `containers` row (its own id doubling as `assignment_id`), and publishing `node.<id>.assign` onto the winning node — then consuming `node.*.status` back to update that row via `assignment_id`. NATS is treated as a hard dependency for this service (unlike the worker's degrade-to-HTTP-only), since the scheduler has no other job. Integration test builds and runs the real scheduler binary plus two real worker binaries against real Postgres + NATS + Docker, publishes a `placement.requested` event, and confirms exactly one `containers` row appears pointing at one of the two registered nodes, that its status reaches `running`, and that the resulting container is actually running on the real Docker daemon. Task 6 done: `handleDeploy` no longer calls the worker over HTTP — it writes the `deployments` row then publishes `placement.requested`, matching `ARCHITECTURE.md` §2.1; a publish failure marks the deployment `failed`, a successful publish leaves it `pending` and relies entirely on the scheduler/worker's own `containers` writes from here on. Added `GET /v1/nodes`, gated by a new `requirePlatformAdmin` check (an explicitly scoped approximation — owner/admin in any org — since no real platform-wide role exists yet). Extended the deployment read path with an `attachPlacement` join through `containers` to surface `node_id`/`container_status`. `deployment.WorkerContainerID` is now a permanent Phase 1 relic (`handleDeploy` never populates it again), which broke and required fixing three downstream consumers: `handleGetLogs`, `handleDeleteApplication`, and the CLI's `get deployments` table (now shows `NODE`/`CONTAINER_STATUS`). The API server's own NATS dependency degrades gracefully (nil bus) rather than failing hard like the scheduler's, since only the deploy route needs it. Both the API server's integration test and `e2e/phase1_test.go` were extended to run a real scheduler + NATS alongside Postgres/worker, fixing along the way a startup-ordering bug (the scheduler's `node.*.register` subscription must be live before the worker's one-shot core-NATS registration publish, or it's lost forever — core NATS has no replay). Known, deliberately deferred gap found in already-shipped Task 5 code: `registry.go`'s heartbeat-for-unregistered-node handler logs "will self-heal on next register/heartbeat" but doesn't actually re-register anything — it just drops the message; a real fix needs new design work since the heartbeat payload lacks the data required to re-register. Task 7 done: added `platform get nodes`, listing every registered node's `ID`/`HOSTNAME`/`STATUS`/`LAST_HEARTBEAT_AT` via the CLI's new `apiclient.ListNodes` calling `GET /v1/nodes`. Unlike `get deployments`, this isn't project-scoped (visibility is gated server-side by `requirePlatformAdmin`, not org/project membership), so it only requires a logged-in session (`requireLogin`), not `requireProject`. Task 8 done: `infrastructure/docker-compose.yml` now brings up `worker-1`/`worker-2`/`worker-3` (new `services/worker/Dockerfile`, multi-stage build), each with a distinct artificial CPU/memory capacity ceiling (2000m/2048MB, 1000m/1024MB, 3000m/3072MB) per ADR-0009, all pointed at `nats` and sharing the host's real Docker daemon via a mounted `/var/run/docker.sock` — not isolated hosts, exactly as the ADR documents. Each worker gets its own named volume for `WORKER_NODE_ID_FILE` so a restart re-registers the same node identity rather than minting a new one. Verified live: `docker compose up nats worker-1 worker-2 worker-3` brings up all three, each registers over NATS with a distinct node ID/hostname within the same tick, and a real `POST /v1/containers` call against `worker-1` actually pulled and started `nginx:latest` on the host daemon through the mounted socket — confirming the socket mount, not just the process wiring, actually works. apiserver/scheduler remain host processes for now (only `postgres`/`nats`/the 3 workers are containerized) — matching Task 8's literal scope, not `docs/local-development.md`'s full aspirational service list. Task 9 done: automated this phase's own exit-criteria script as `e2e/phase2_test.go` (`TestE2E_Phase2ExitCriteria`, `go test -tags=e2e ./e2e/...`), mirroring Phase 1's exit-criteria test's real-binaries-as-real-OS-processes discipline — builds and runs a real `apiserver`, `scheduler`, and 3 real `worker` processes against real testcontainer Postgres + NATS, all driven through the compiled `platform` CLI binary: deploy nginx → poll `get deployments`/`get nodes` until the scheduler places it on one of the 3 (confirming all 3 report `healthy` first) → hard-kill that specific worker's OS process → poll `get nodes` until just that node reports `unreachable` while the other two stay `healthy`. Passes reliably in ~50s (verified with repeated fresh runs, `-count=1`). Sped up the scheduler's liveness sweep (`SCHEDULER_HEARTBEAT_TIMEOUT=3s`/`SCHEDULER_LIVENESS_SWEEP_INTERVAL=1s`) and the worker's heartbeat (`WORKER_HEARTBEAT_INTERVAL=1s`) via their existing env-var tunables so the test doesn't have to eat the 15s/5s production defaults. Along the way, found and fixed a real container leak: unlike Phase 1's script, this phase's exit-criteria script has no delete step, so the deployed nginx container would otherwise leak on every test run (confirmed happening before the fix); added a before/after `docker ps` diff in the test itself (shelling out to the `docker` CLI, not the SDK — ADR-0011 reserves direct Docker client imports for `internal/runtime` alone) that force-removes exactly the one container this test created. Also confirmed, while diagnosing that leak, a real latent bug worth flagging separately: `handleDeleteApplication`'s post-Task-6 fix routes container stop/remove through the single fixed `WORKER_ADDR` HTTP client regardless of which node a deployment actually landed on — in a true multi-node deployment (unlike this test, where nodes conveniently share one Docker daemon), deleting an application placed on a node other than the one `WORKER_ADDR` points at would silently no-op (the wrong worker's "container not found" is treated as an acceptable outcome) rather than actually stopping the real container. Not fixed here — out of Task 9's scope, needs `handleDeleteApplication` to route through the deployment's actual placed node instead of a single hardcoded worker address, which likely wants its own tracked task.
