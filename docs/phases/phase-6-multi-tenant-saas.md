# Phase 6 — Multi-Tenant SaaS Layer: Detailed Task Plan

Parent scope: `ARCHITECTURE.md` §10 (Phase 6 entry), §2.9 (Tenant Quota Enforcement pattern), §9 risk register R4 (tenant isolation), `database-schema.md` §2 (`resource_quotas`, `audit_logs` — migration slots 0010/0011 already reserved) and §3 (RLS/denormalization rules), `docs/rbac-multitenancy.md` (the full permission matrix and required test coverage), `docs/api-conventions.md` (routes already named for orgs/members/audit-logs/rollback), ADR-0004 (multi-tenant schema from day one), ADR-0008 (JWT + API-key auth), ADR-0010 (defense-in-depth tenant isolation). This doc breaks that scope into implementable, orderable tasks with acceptance criteria, mirroring `docs/phases/phase-2-multi-node.md` through `phase-5-networking-ingress.md`'s format.

Exit criteria for the whole phase (restated from `ARCHITECTURE.md` §10):

```text
R4's cross-tenant-access integration tests pass; a developer-role user is
denied an organization.manage action server-side even if the frontend
check is bypassed
```

Phases 1-5 built every tenant-scoped resource type (projects, applications, deployments, domains) with RLS from day one (ADR-0004/0010) and a working `requirePermission`/`requireMembership` mechanism, but only wired permissions for the resources that already existed — the matrix in `rbac-multitenancy.md` §2 has thirteen rows and only seven are wired to a real permission constant today, and several of those thirteen rows have no route to gate at all yet because the underlying feature (organization settings, member management, API keys, audit log, quotas) was never built. Phase 6's job is closing that gap: build the remaining features the matrix already names, wire every mutating route in the entire API surface (old and new) to the right permission, and add the systematic cross-tenant/permission-matrix test coverage `rbac-multitenancy.md` §5 requires but has so far only been applied piecemeal, one resource at a time, as each phase shipped it.

## Current state (what already exists vs. what Phase 6 builds)

- **Already shipped, reused as-is**: `internal/auth.HasPermission`/`permissionMatrix`, `requirePermission`/`requireMembership` (`services/apiserver/internal/server/permission.go`), the two-branch RLS policy shape, `MembershipRepository.RoleForUser`. No new authorization *mechanism* — Phase 6 fills in permission constants and routes, it doesn't rebuild the middleware layer `rbac-multitenancy.md` §3.1 already describes as done.
- **Partially wired**: `application.create/delete/deploy`, `project.create`, `domains.manage`, `logs.view` are the only matrix rows with both a `Permission` constant and a gating route today. `PATCH /v1/applications/:appId` (scale) reuses `PermApplicationDeploy` rather than a distinct `application.scale` constant, even though the matrix lists them as separate rows (see open decision 1).
- **Table exists, zero application code**: `api_keys` (migration `0002`, RLS already in place, Phase 1) — no repository, no routes, no CLI, and `auth.Authenticate` only ever verifies JWTs today even though `api-conventions.md` §3 already specifies the `Bearer <api_key>` format.
- **Nothing exists yet**: `resource_quotas`, `audit_logs` (migrations `0010`/`0011` are reserved slots, not applied), organization settings/delete routes, member list/invite/remove/role-change routes. `env_vars` (migration `0004`) is the same story as `api_keys` — table only, no feature — but building it is a Phase 6 non-goal (see deferred list).
- **`resource_usage_samples`** (migration `0012`) is *not* Phase 6 scope despite being adjacent in the migration list — it backs Phase 9's dashboards ("sourced from real worker-reported data"), and quota enforcement here only needs current-state `COUNT`/`SUM` queries against tables that already exist (`projects`, `applications`, `containers`), not a time-series table.

## Task sequence

Tasks are ordered by dependency — each assumes the ones above it exist.

### 1. DB: `resource_quotas` + `audit_logs` migrations + repositories
- `0010_resource_quotas.sql` per `database-schema.md` §2: one row per org (`org_id pk fk→organizations`, `max_cpu_millicores`, `max_memory_mb`, `max_containers`, `max_projects`, `max_deployments_per_day`), created in the same transaction as the org itself (`handleSignup`'s existing bootstrap, Task 2's own wiring) with placeholder defaults in the same spirit as every other untuned constant this codebase carries (`R9`-style — e.g. `max_projects=10`, `max_containers=20`, `max_cpu_millicores=8000`, `max_memory_mb=16384`, `max_deployments_per_day=100`), revisit with real usage data later. `QuotaRepository` in `internal/db` (ADR-0011): `Create` (called from the signup transaction), `Get(orgID)`, `CurrentUsage(orgID)` (live `COUNT`/`SUM` against `projects`/`applications`/`containers`, not a cached counter — correctness over speed at this scale).
- `0011_audit_logs.sql` per `database-schema.md` §2: append-only (`REVOKE UPDATE, DELETE` on the table for the app DB role, not just convention — the doc's own words), `id pk`, `org_id fk`, `actor_user_id fk→users nullable`, `action text`, `target_type text`, `target_id uuid`, `metadata jsonb`, `created_at`. `AuditLogRepository`: `Record(ctx, entry) error` and `ListByOrg(orgID, cursor, limit)` (cursor-based per `api-conventions.md` §4, same shape the doc's own `GET /v1/orgs/:orgId/audit-logs` example already uses).
- Acceptance: repository-level integration tests against real Postgres — quota row created alongside a new org, `CurrentUsage` reflects real counts after seeding projects/containers, audit log insert-then-list round-trips, and a direct `UPDATE`/`DELETE` attempt against `audit_logs` fails at the DB level regardless of role.

### 2. RBAC completeness pass
- Add every remaining `Permission` constant from `rbac-multitenancy.md` §2 to `internal/auth/rbac.go`'s matrix: `PermOrganizationManage`, `PermOrganizationDelete`, `PermMembersInvite`, `PermMembersRemove`, `PermMembersChangeRole`, `PermEnvVarsWrite` (constant only — no route until env vars ships, if ever; see deferred list), `PermAuditLogsView`, `PermAPIKeysCreate`, `PermAPIKeysRevoke`, `PermBillingView` (constant only — no billing system exists or is planned in any phase; kept so the matrix and its unit test stay complete, not because a route is coming), `PermMetricsView` (constant only — metrics don't exist until Phase 9), `PermDeploymentRollback` (constant only — automatic rollback is Phase 8; no manual-rollback route is built here, see deferred list).
- Decide `application.scale` (open decision 1): add `PermApplicationScale` as its own constant with the same allow-set as `PermApplicationDeploy`, and switch `handleScaleApplication` to it — the matrix lists them as two rows for a reason (a future role split shouldn't require touching handler code), even though their current values are identical.
- Full existing-route audit: confirm every mutating route added in Phases 1-5 (`applications`, `deployments`, `domains`, `projects`) calls `requirePermission` with the matrix-correct constant — this task is the retrofit checkpoint for anything Phase 1-5 shipped without the full matrix to check against yet. `permission.go`'s doc comments/behavior are otherwise unchanged.
- Acceptance: `rbac_test.go`'s table extended to cover every matrix row (all four roles × every permission) — this becomes the literal, complete transcription of `rbac-multitenancy.md` §2 the doc's own text says it should be.

### 3. API + CLI: organization management
- `PATCH /v1/orgs/:orgId` `{name}` — settings update, gated by `organization.manage`. `DELETE /v1/orgs/:orgId` — gated by `organization.delete` (owner only, per the matrix). `OrganizationRepository` gains `Update`/`Delete`.
- `platform get org`, `platform update org --name <name>` (CLI already tracks `cfg.OrgID`/`cfg.OrgSlug` from signup — no new "which org" selection concept needed, single-org-per-session stays exactly Phase 1's model). No `platform delete org` CLI command yet — deleting your only org from a CLI session that's currently authenticated against it is a genuine UX foot-gun (open decision 2); the route exists and is tested, the CLI surface for it is deferred until there's a real second-org-to-fall-back-to story.
- Acceptance: integration tests for the permission-matrix check (owner/admin allowed on `organization.manage`, only owner on `organization.delete`, developer/viewer denied on both) and cross-tenant denial (404) on both routes.

### 4. API + CLI: member management
- `GET /v1/orgs/:orgId/members` (membership-only, no permission beyond being a member — same posture as `logs.view`), `POST /v1/orgs/:orgId/members` `{email, role}` (gated by `members.invite`), `DELETE /v1/orgs/:orgId/members/:userId` (gated by `members.remove`), `PATCH /v1/orgs/:orgId/members/:userId` `{role}` (gated by `members.change_role`). `MembershipRepository` gains `ListByOrg`, `UpdateRole`, `Delete`.
- Open decision 3: "invite" only works for an **already-registered** user, looked up by email via `UserRepository` and added directly to the target org's memberships — there is no email-sending infrastructure anywhere in this codebase, so a real invite-token/verification-email flow is out of scope. Inviting an email with no account returns a clear `404`/error telling the caller that person needs to sign up first, not a silent no-op or a half-built invite-token table nothing else uses.
- Guard against locking an org out of ownership: `members.remove`/`members.change_role` reject removing or demoting the org's last remaining `owner` (a small application-layer check, not a matrix permission — the matrix says an owner *can* do this to others, not that the org can end up with zero owners).
- `platform get members`, `platform invite <email> --role <role>`, `platform remove-member <email>`, `platform set-role <email> <role>`.
- Acceptance: integration tests covering the full flow, the permission-matrix check per route, cross-tenant denial, the last-owner guard, and inviting an unregistered email's error path.

### 5. API + CLI: API keys
- `APIKeyRepository`: `Create` (generates a random key, stores only its SHA-256 hash — the plaintext is returned exactly once, at creation, never stored or retrievable again, standard practice), `ListByOrg`, `Revoke`, `LookupActiveByHash` (the auth-path query). Key format `pk_live_<32 random bytes, base62>` per `api-conventions.md` §3's own already-specified prefix convention.
- `POST /v1/orgs/:orgId/api-keys` `{name, scopes}` (gated by `api_keys.create`), `GET /v1/orgs/:orgId/api-keys` (gated by `api_keys.create` too — matrix has no separate list permission, and only owner/admin can create per the matrix, so only they can see the list), `DELETE /v1/api-keys/:keyId` (gated by `api_keys.revoke`, deep-by-ID per `api-conventions.md` §2).
- Wire the auth path: `auth.Authenticate` currently only tries `VerifyAccessToken`; extend it to distinguish by the `pk_live_` prefix (`api-conventions.md` §3) and, on that prefix, hash-and-look-up against `APIKeyRepository.LookupActiveByHash` instead, injecting the key's `org_id` directly (an API key is scoped to one org already, unlike a user's JWT which can belong to several) — routes that currently resolve org from a user's membership need a small adjustment to accept an already-known org from the API-key path.
- `platform create api-key <name>`, `platform get api-keys`, `platform delete api-key <name>` — the plaintext key is printed exactly once, at creation, with an explicit "save this now, it won't be shown again" message.
- Acceptance: integration tests covering create/list/revoke, the permission-matrix check, cross-tenant denial, a revoked key's requests being rejected, and at least one existing route (e.g. `GET /v1/applications/:appId/deployments`) successfully authenticated via an API key end to end — proving the auth-path wiring actually works, not just the CRUD routes.

### 6. Quotas: three-layer enforcement (`ARCHITECTURE.md` §2.9)
- **Layer 1 — API server**: before `project.create` succeeds, check `CurrentUsage(orgID).Projects < quota.MaxProjects`; before `deploy`/`scale` succeeds, check the resulting total container count and total CPU/memory against `MaxContainers`/`MaxCPUMillicores`/`MaxMemoryMB`; before `deploy` succeeds, check today's deployment count against `MaxDeploymentsPerDay`. A violation returns `422` with the standard error envelope (`api-conventions.md` §4) — `code: "quota_exceeded"`, exactly the doc's own worked example.
- **Layer 2 — scheduler re-check**: at placement time (closing the TOCTOU gap between the API's check and the container actually landing on a node — e.g. two concurrent scale requests both passing the API check before either commits), the scheduler re-verifies `MaxContainers`/CPU/memory against current usage before writing the `containers` row, rejecting placement (and reporting failure back the same way an unschedulable-for-capacity assignment already does) if the org would exceed quota.
- **Layer 3 — Postgres backstop**: a trigger on `containers` insert (and `projects` insert for `max_projects`) that rejects if the owning org's post-insert count would exceed its `resource_quotas` row — the last-resort layer per §2.9, expected to essentially never fire if layers 1/2 are correct, existing purely as defense in depth (§9 R4's own reasoning applied to quotas, not just isolation).
- `platform get quota` (current usage vs. limit per resource, CLI-only — no update route in this task; quota limits themselves are platform-operator-set, not self-service, so there's deliberately no `platform set quota` here).
- Acceptance: integration tests for each of the three layers independently (API rejects at the limit, scheduler rejects a placement that would have slipped past a stale API-layer count, the DB trigger rejects a direct insert that bypasses both), plus one test proving all three agree on the same boundary (an org at exactly its limit is rejected consistently by all three, not just one).

### 7. Audit log: write path + read route
- Every mutating route across the *entire* API surface — not just Phase 6's own new routes, but the Phase 1-5 routes too (`projects`, `applications`, `deployments`, `domains`, plus everything Tasks 3-6 add) — records one `audit_logs` row (`actor_user_id`, `action` e.g. `"application.delete"`, `target_type`, `target_id`, `metadata`) in the same transaction as the mutation itself.
- Open decision 4: written **synchronously, in-transaction**, not via a NATS-subscribed audit-logger service, even though `ARCHITECTURE.md` §3's own table frames "audit log" as a NATS-subscriber use case. Reasoning: most Phase 1-5 mutating actions (project/domain/org/member CRUD) don't currently publish any NATS event at all — only cluster-runtime changes do (`service.updated`, `placement.requested`) — so an event-driven audit logger would need a new published event for every administrative action anyway, at which point in-transaction is strictly simpler and gives audit correctness a stronger guarantee (no risk of a lost/never-consumed event silently producing an incomplete audit trail, which defeats the feature's entire purpose in a way that's tolerable for service-discovery caching but not for an audit log). Revisit if audit-log write latency ever becomes a measured problem on the request hot path — it isn't one today.
- `GET /v1/orgs/:orgId/audit-logs?limit=&cursor=` (gated by `audit_logs.view`, cursor pagination per `api-conventions.md` §4's own worked example on this exact route). `platform get audit-log`.
- Acceptance: integration test confirming a representative sample of mutating actions (one from each of projects/applications/domains/orgs/members/api-keys) produces a matching audit row, cross-tenant denial and permission-matrix checks on the read route, and a direct `UPDATE`/`DELETE` against the table failing regardless of caller role (re-confirms Task 1's DB-level guarantee end-to-end through the API's own connection role).

### 8. Required RBAC/tenant-isolation test sweep
- `rbac-multitenancy.md` §5's three required-coverage items, applied as one consolidated pass across every resource type that exists by now (not just Phase 6's new ones): cross-tenant denial (404) for every resource type, a full permission-matrix table-driven test (every row × every role, ideally one shared table-driven test structure reused per resource rather than N hand-copies), and a role-change-takes-effect-immediately test (change a membership's role mid-session, confirm the very next request re-checks Postgres, not the still-valid JWT's claims — `ADR-0008`'s own reasoning for not trusting authorization from the token).
- This is a coverage audit/consolidation task, not new product surface — expect it to mostly confirm Tasks 1-7's own tests already satisfy §5, and to fill in specifically what's missing (e.g. Phase 1-5 resources whose cross-tenant test exists but whose full-matrix test only ever covered the roles that specific PR's author thought to check).
- Acceptance: a single place (new or consolidated test file) that, read top to bottom, is a checkable transcription of `rbac-multitenancy.md` §2's entire table having real test coverage — this is what makes the phase's own exit criteria's first clause ("R4's cross-tenant-access integration tests pass") a checkable statement rather than an assertion.

### 9. End-to-end test automation
- Automate this phase's exit criteria as `e2e/phase6_test.go` (`-tags=e2e`), following the exact real-binaries-as-real-OS-processes pattern `e2e/phase1_test.go` through `phase5_test.go` established.
- Script: two users, two orgs (or one org with a seeded `developer`-role member) → the cross-tenant scenario (org A's developer cannot read/write org B's resources) → the literal exit-criteria assertion: a `developer`-role user's raw HTTP request to `PATCH /v1/orgs/:orgId` (an `organization.manage` action) is rejected `403` server-side, sent directly over HTTP rather than through the CLI — proving the enforcement is real even if a client-side check were bypassed, exactly the exit criteria's own wording.
- Acceptance: this test is what actually certifies Phase 6 done, exactly as Phase 1 Task 8 through Phase 5 Task 6 did for their phases.

## Explicitly deferred out of Phase 6

- **The dashboard UI itself.** `ARCHITECTURE.md` §10 names "org/project UI" as a Phase 6 deliverable, but `apps/dashboard/README.md` has deferred it since Phase 1 ("scaffolded when a phase actually needs it"), no phase through Phase 5 has touched it, and the phase's own literal exit criteria (restated above) is entirely server-side/CLI-testable — the "frontend check... bypassed" wording describes the *threat model* server-side enforcement must survive, not a requirement that a frontend exists to bypass. Recommendation: **keep deferring it** — every Phase 6 feature gets full CLI parity (Tasks 3-7) exactly like every prior phase's admin surface, and the dashboard scaffold is picked up whenever a phase's plan actually commits to building it (this doc's own recommendation, confirm-or-override during review like every other open decision below).
- **`env_vars` (secrets management).** Table exists since migration `0004`, but no phase has ever built the create/read/update routes or CLI for it, and Phase 6 is enforcement of what's specified, not a good place to also originate a brand-new deploy-time feature with its own envelope-encryption-key-handling design questions. `PermEnvVarsWrite` is added to the matrix for completeness (Task 2) with no route to gate — flagged the same way `billing.view`/`metrics.view` are.
- **Real ACME-style API-key scopes enforcement.** `api_keys.scopes text[]` exists in the schema and is accepted at creation (Task 5), but nothing in this phase's routes actually restricts an API key to a subset of what its owning role could otherwise do — every route an API key can authenticate to is still gated by the *role* of `created_by`, not by `scopes`. Fine-grained scope checking is real design work (what does a "scope" even name — a permission? a resource? a route?) with no concrete driver yet (`modularity-and-extensibility.md` §6's "don't build speculative generality" applies).
- **Manual deployment rollback route.** `POST /v1/deployments/:deploymentId/rollback` is named in `api-conventions.md` §2 and `deployment.rollback` is a matrix row, but automatic rollback (with real health-check-triggered logic) is Phase 8's whole deliverable — building a bare manual-trigger version now would mean redesigning it again in two phases. `PermDeploymentRollback` is added to the matrix (Task 2) with no route yet, same treatment as `env_vars.write`.
- **Rate limiting.** Named in `api-conventions.md` §5 with response-header conventions already specified, but it's explicitly Phase 11 scope (`ARCHITECTURE.md` §10's security-hardening phase), not Phase 6.
- **`resource_usage_samples` / real usage metrics.** Phase 9's deliverable (see "Current state" above) — quota enforcement here only needs live `COUNT`/`SUM` queries, not a sampled time series.
- **Custom/user-definable roles.** `rbac-multitenancy.md` §1 explicitly fixes the four-role set "for the MVP-through-Phase-6 timeframe" — Phase 6 is the last phase that gets to assume this, not the phase that changes it.

## Open implementation decisions (resolved here, confirm before coding)

1. **`application.scale`**: give it its own `PermApplicationScale` constant (same allow-set as `application.deploy` today, but decoupled so a future role split doesn't require a handler change) rather than continuing to reuse `PermApplicationDeploy`.
2. **`platform delete org` CLI command**: route exists and is tested (Task 3), but no CLI surface for it yet — deleting the only org a CLI session is authenticated against is a real UX foot-gun without a "what happens to my session next" story, not worth guessing at without a concrete need.
3. **Member invite scope**: existing-registered-users-only, looked up by email — no email-sending/invite-token infrastructure exists anywhere in this codebase, and building one is a much larger feature than "wire the matrix's existing `members.invite` row to a route."
4. **Audit log write path**: synchronous, in-transaction with the mutation it records, not NATS-subscriber-driven — despite `ARCHITECTURE.md` §3's table framing audit log as a pub/sub consumer, most Phase 1-5 administrative actions don't publish any event today, and an audit trail's correctness guarantee is worth more than the decoupling a subscriber model would buy here.
5. **API-key scoping**: `scopes` is stored but not enforced beyond the key owner's own role (see deferred list) — full scope enforcement needs a concrete design question answered first (scope = permission? resource? route?) that no current use case forces yet.
