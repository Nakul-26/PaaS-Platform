# Phase 7 — Deployment Platform (Git → build → deploy): Detailed Task Plan

Parent scope: `ARCHITECTURE.md` §10 (Phase 7 entry), `docs/modularity-and-extensibility.md` §2 (the already-named `ImageBuilder` port, pinned to `services/image-builder/internal`, adapter "Docker build (Phase 7)", future alternatives Buildpacks/Nixpacks/Kaniko) and §3 (the already-reserved `image-builder` network-contract row: "NATS or REST trigger (build requested), publishes build-complete events"), `docs/database-schema.md` §4 (next migration slot), `docs/api-conventions.md`, `docs/nats-contract.md` (subject/transport conventions), `docs/rbac-multitenancy.md` §2. This doc breaks that scope into implementable, orderable tasks with acceptance criteria, mirroring `docs/phases/phase-2-multi-node.md` through `phase-6-multi-tenant-saas.md`'s format.

Exit criteria for the whole phase (restated from `ARCHITECTURE.md` §10):

```text
deploy from a Git repo URL without manually building/pushing an image first
```

Every phase through 6 assumed a caller already has a pushed image (`--image` on `deploy`). Phase 7 adds a second input mode — a Git repo URL — that the platform itself turns into a running deployment: clone, build a Docker image from a `Dockerfile` at the repo root, push it to a registry, then deploy it, all from one CLI invocation. `ARCHITECTURE.md` already reserved room for this (the `services/image-builder/` stub in §5's repo layout, the `ImageBuilder` row in the modularity registry) but has no `§2.x` component section describing it yet, unlike every other service — Task 1 below closes that gap as its first step, per this project's own rule (`ROADMAP.md`, "How to update this file") that a real implementation diverging from or extending `ARCHITECTURE.md` gets folded back into that document, not left as drift.

## Task sequence

Tasks are ordered by dependency — each assumes the ones above it exist.

### 1. `ARCHITECTURE.md` §2.10 + DB: `builds` migration + repository
- Add `### 2.10 Image Builder **[INSTANCE: Go process + Docker Engine SDK]**` to `ARCHITECTURE.md` §2, same bullet-list format as §2.1-2.9: clones a Git repo (public only — see Open Decision 4), builds an image from a `Dockerfile` at its root via the Docker Engine API, pushes it to a registry, reports outcome over NATS; behind an `ImageBuilder` port exactly as `docs/modularity-and-extensibility.md` already specifies (package location, adapter, future alternatives — no change needed to that doc, this just gives it a `§2` home).
- `0014_builds.sql`: `builds(id pk, org_id fk, application_id fk→applications, git_url text, git_ref text not null default 'main', commit_sha text nullable, status enum(pending|cloning|building|pushing|succeeded|failed), image text nullable, error_message text nullable, created_by fk→users, created_at, completed_at nullable)`. Tenant-authored config like `domains`, not cluster-observed state like `containers` — RLS enabled, same two-branch policy shape (`database-schema.md` §3) as every other tenant table. Index on `(application_id, created_at DESC, id DESC)` for `ListByApplication`'s cursor pagination (same shape as `DeploymentRepository.ListByApplication`/`AuditLogRepository.ListByOrg`).
- `BuildRepository` in `internal/db`: `Create(orgID, appID, gitURL, gitRef, userID) (Build, error)`, `ListByApplication(appID, limit, cursor)`, `OrgID(id)` (deep-by-ID, `api-conventions.md` §2), `UpdateResult(id, status, commitSHA, image, errMsg)` — same shape as `DeploymentRepository.UpdateResult`.
- Acceptance: repository-level integration test against real Postgres — create/list/cursor-pagination/RLS cross-tenant isolation, mirroring `TestAuditLogRepository`'s/`TestQuotaRepository`'s own coverage shape.

### 2. Local registry (`infrastructure/docker-compose.yml`)
- Add the official `registry:2` image as a new `registry` service, matching the project's existing precedent of self-contained local infra (Postgres/NATS testcontainers in tests, `registry:2` here) rather than requiring a real Docker Hub/ECR account for local dev or CI. Plain HTTP, no auth — same "local dev is a logical simulation, not production" posture ADR-0009 already established for worker node capacity.
- New shared config value `IMAGE_REGISTRY_ADDR` (default `localhost:5000`), consumed by Task 3 (image-builder pushes here) — no consumer needs to *pull* through it directly in this phase; the worker's existing `ContainerRuntime.PullImage` already accepts an arbitrary image reference string unchanged, so a deploy of a repo-built image needs zero worker-side code changes.
- Acceptance: `docker compose up registry` comes up; a manual `docker push localhost:5000/test:latest` / `docker pull` round-trip confirms it's reachable and unauthenticated, matching local-development.md's existing verification style for new compose services.

*(Independent of Task 1 — can run in parallel.)*

### 3. `services/image-builder`: clone, build, push
- New binary + `internal/imagebuilder` package (per the modularity registry's pinned location `services/image-builder/internal`) — the `ImageBuilder` port (`Build(ctx, gitURL, gitRef, imageTag) (commitSHA string, err error)`) and its one Docker-build adapter, following ADR-0006's precedent of confining Docker SDK usage to a single package rather than spreading `docker/docker/client` imports across the codebase (ADR-0011).
- Git fetch is a plain internal function, not a named port: shells out to the system `git` binary (`git clone --depth 1 --branch <ref> <url> <tmpdir>`, bounded by a configurable timeout) rather than a Go git library or a new interface — no documented alternative driver exists yet, and `modularity-and-extensibility.md` §6 is explicit that an interface needs a concrete reason, not just "to be safe." Public repos only (Open Decision 4).
- Subscribes durably (JetStream, new stream `BUILDS`) to `build.requested`; on message, clones, resolves the ref to its commit SHA, runs a Docker build (`docker.ImageBuild` against the cloned dir) tagged `<IMAGE_REGISTRY_ADDR>/<org_id>/<application_id>:<commit_sha>` (per-org path segment keeps the shared local registry's namespace collision-free without needing per-tenant auth), pushes it, then publishes `build.completed` — one subject for both outcomes, payload carrying `status: succeeded|failed` (+ `image`/`commit_sha` or `error`), mirroring `node.<id>.status`'s existing "one subject, a status field carries the branch" precedent rather than splitting into two subjects.
- Needs the same Docker-daemon-socket access the worker containers already have in `docker-compose.yml` (ADR-0009's "not isolated hosts" precedent) — no new trust boundary in kind, but a materially wider one in practice: this is the first place tenant-supplied code (a Dockerfile's `RUN` steps, and the repo content itself) executes during a request this platform serves, not just a tenant-*selected* pre-built image. Flagged explicitly, not solved here — real isolation (e.g. Kaniko rootless builds, already `modularity-and-extensibility.md`'s named future `ImageBuilder` alternative for exactly this reason) is out of Phase 7's scope; see "Explicitly deferred" below.
- Acceptance: integration test — build a real small public repo (a fixture repo or a trivial inline `Dockerfile`-only fixture checked into `e2e/testdata` to avoid a live network dependency in CI) against a real local registry container, confirm the resulting image is pullable by tag and `build.completed` carries the right commit SHA/image reference; a bad `Dockerfile`/nonexistent ref produces `build.completed{status:"failed"}` with a populated `error`, not a hung consumer.

*(Depends on Task 1's NATS contract shape and Task 2's registry address.)*

### 4. API server: git-based deploy request + build-completion consumer
- Extract `handleDeploy`'s "create a `deployments` row + publish `placement.requested`" body (`services/apiserver/internal/server/handlers_deployments.go`) into a shared unexported helper, callable both from the existing HTTP path (`--image`) and this task's new NATS consumer (`--git`) — the two paths must run the identical quota-check-then-create-then-publish sequence, not a second hand-copied one.
- `POST /v1/applications/:appId/deployments` accepts `git_url`/`git_ref` as an alternative to `image` (mutually exclusive — `errBadRequest` if both or neither are set). The git path: runs the same `checkDeploymentQuota`/`checkResourceQuota` pre-check `handleDeploy` already does for the image path (early rejection before spending any build time — Layer 1, unchanged posture from Task 6/phase-6), creates a `builds` row (`status: pending`), records `build.create` via the existing `recordAudit` helper, and publishes `build.requested` — returns `202 Accepted` with the build's id/status (not `201` with a deployment, since none exists yet).
- New durable consumer on `build.completed`: on `succeeded`, calls Task 4's extracted shared helper to create the `deployments` row + publish `placement.requested`, using the build row's stored `created_by` as the actor for its `deployment.create` audit entry (no live HTTP request/context to pull a user ID from, same reasoning `controller-manager`'s reconcile loops already establish for acting without a request-scoped session — see `internal/db.ReconcileRepository`'s doc comment); on `failed`, only updates the `builds` row (`UpdateResult`) — no further action, no audit entry (mirrors Phase 6 Task 7's existing "system state transitions aren't audited, only the initiating user action is" line, drawn here between "user requested a build" and "the build finished").
- New `GET /v1/applications/:appId/builds` — `requireMembership` only (read-only, same posture as `GET .../deployments`), cursor-paginated identically to `handleGetDeployments`.
- No new RBAC permission — a git-based deploy request is gated by the existing `application.deploy` (`rbac-multitenancy.md` §2 doesn't distinguish "how" a deploy was triggered, only that one was).
- Acceptance: integration test — `POST .../deployments` with `git_url` set produces a `builds` row and a `build.requested` publish (asserted via a direct NATS subscribe, no real image-builder needed, same "not standing up every downstream service" posture `TestAPIServer_Quotas` already established for the scheduler); a second test publishes a synthetic `build.completed{status:"succeeded"}` directly and confirms a `deployments` row appears with the right image and `placement.requested` fires; a third confirms `status:"failed"` only updates `builds`, never creates a deployment; permission-matrix + cross-tenant-404 coverage on both new/changed routes, same sweep discipline `rbac_sweep_test.go` (Phase 6 Task 8) established.

*(Depends on Task 1's `builds` table/repository; the NATS subject shape is Task 3's contract but this task's own tests don't need a real image-builder process.)*

### 5. CLI: `deploy --git` + `get builds`
- `platform deploy <app-name> --git <repo-url> [--ref <branch-or-tag>] [--dockerfile <path>]` as an alternative to `--image` on the existing `deploy` command (mutually exclusive, validated client-side before the request for a fast error, same posture `parsePortFlags` already uses for `--port`). `--dockerfile` is accepted and threaded through to the request/`builds` row now even though Task 3's builder only supports a repo-root `Dockerfile` in this phase (open decision below) — avoids a breaking flag addition later.
- On success, prints the build id and a note to poll `platform get builds <app-name>` rather than blocking the command on the async build (matching `deploy`'s existing non-blocking posture — it already doesn't wait for placement today).
- `platform get builds <app-name>` — lists builds newest-first (`STATUS`, `GIT_REF`, `COMMIT`, `IMAGE` once succeeded, `ERROR` once failed), same table-command shape as `get deployments`/`get audit-log`.
- Acceptance: manual/integration check against a real apiserver, same lighter bar phase-5's Task 3 used for its own CLI task (the permanent automated coverage is Task 6's e2e test).

*(Depends on Task 4's API routes.)*

### 6. End-to-end test automation
- Automate this phase's exit criteria as `e2e/phase7_test.go` (`-tags=e2e`), following the exact real-binaries-as-real-OS-processes pattern `e2e/phase1_test.go` through `phase6_test.go` established — this run additionally builds and starts a real `image-builder` process and a real local `registry:2` container alongside the existing `apiserver`/`scheduler`/`worker`/`controller-manager` set.
- Script: `platform deploy <app> --git <fixture-repo-url>` → poll `get builds` until `succeeded` → poll `get deployments` until `1/1` running → curl the running container's mapped port to confirm it's actually serving the fixture app, not just that the DB rows look right. Uses the same checked-in trivial fixture (Task 3) rather than a live network dependency, keeping this test as hermetic as every prior phase's e2e test.
- Acceptance: this test is what actually certifies Phase 7 done, exactly as Phase 1 Task 8 through Phase 6 Task 9 did for their phases.

## Explicitly deferred out of Phase 7

- **Private repos / Git authentication** (SSH keys, PATs, deploy tokens) — Phase 7 only clones public URLs; no credential storage or injection exists yet. A real implementation needs its own encrypted-secret design (same envelope-encryption precedent `env_vars.value_encrypted` already established), not guessed now.
- **Non-Dockerfile build strategies** (Buildpacks, Nixpacks) — `modularity-and-extensibility.md` already names these as the `ImageBuilder` port's documented future alternatives; Docker-build-from-a-root-`Dockerfile` is the whole Phase 7 deliverable.
- **Sandboxed/rootless build isolation** (e.g. Kaniko) — flagged in Task 3 as a real, widened trust boundary (tenant-supplied build steps, not just tenant-selected images, now execute with Docker-daemon-socket access); the modularity doc already names Kaniko as the future alternative for exactly this reason. Out of scope until a dedicated hardening pass (candidate: Phase 11).
- **Build caching / layer reuse across builds** — every build is a fresh `git clone` + full Docker build; no registry-side or local layer cache. A real optimization needs usage data to size correctly, same "untuned, revisit later" posture every placeholder constant in this codebase already carries.
- **Live build log streaming to the CLI** — `builds.error_message` carries only a terminal failure reason, not a full build log tail. Real log streaming during a build is `docs/nats-contract.md`/Phase 9 Observability's job (the existing container-log-streaming pipeline is a plausible template, not built here).
- **Build cancellation, concurrent-build-per-app limits, or a build queue depth cap beyond NATS's own natural queuing** — no driver for any of these yet; revisit if real usage shows a need.
- **A real (non-local) container registry adapter** (ECR/GCR/Docker Hub) — the local `registry:2` container is Phase 7's whole registry story, matching the project's local-dev-is-a-logical-simulation precedent; swapping it for a real hosted registry is a config/credentials change, not new code, whenever it's actually needed.
- **Dashboard UI for any of this** — CLI parity only, same deferral Phase 6 already made and the roadmap accepted.

## Open implementation decisions (resolved here, confirm before coding)

1. **Build-completion transport**: JetStream `build.requested`/`build.completed` (new `BUILDS` stream), not REST — even though `modularity-and-extensibility.md` §3 left "NATS or REST" open. A lost build request or completion event is exactly the "unacceptable loss" case `docs/nats-contract.md`'s existing table already uses to justify JetStream for `placement.requested`/`node.<id>.assign`; the same reasoning applies here, and it keeps the pattern consistent with every other async cross-service trigger already in this system rather than introducing a second, REST-based one.
2. **Auto-deploy on build success**: the `build.completed` consumer (Task 4) creates the `deployments` row and publishes `placement.requested` itself — no second explicit user action required. This is a literal reading of the exit criteria's own wording ("deploy ... without manually building/pushing an image first" implies one command, not two), and it's why Task 4 extracts `handleDeploy`'s core logic into a shared helper rather than duplicating it.
3. **Image tag / registry namespacing**: `<IMAGE_REGISTRY_ADDR>/<org_id>/<application_id>:<commit_sha>`. Org-then-application path segments keep the shared local registry collision-free across tenants without needing per-tenant registry auth (out of scope — see deferred list); the commit SHA (not a build UUID) makes the tag independently meaningful/reproducible outside this system's own bookkeeping.
4. **Public repos only, Dockerfile-at-root only**: no Git auth, no `--dockerfile` path support beyond accepting-but-not-yet-honoring the flag (Task 5). Keeps Task 3's builder simple for a first working version; both are named, bounded follow-ups above, not silent gaps.
5. **Quota re-check at build-completion time**: not done. `checkDeploymentQuota`/`checkResourceQuota` run once, at build-*request* time (Task 4, same as the image path today) — nothing about an org's quota changes between a build being requested and it finishing, so re-checking would be redundant with Layer 1's own already-established scope; Layers 2 (scheduler) and 3 (Postgres trigger) still apply unchanged at actual placement time regardless of which path produced the `deployments` row.
